# How it works

Agent Monitor derives everything it shows from local files that Claude Code already writes, plus the operating-system process list. It works the same way on Windows and Linux; where the two differ, this page says so.

## Data sources

Under the Claude config directory (`CLAUDE_CONFIG_DIR`, or `~/.claude/` by default):

- **Session registry** - `sessions/*.json`. Each running Claude Code process writes one file containing its PID, session ID, working directory, name, kind, start time (`startedAt`), original process start time (`procStart`), its native status with the time it last changed (`statusUpdatedAt`), the Claude Code version it runs (`version`), and - while Remote Control is on - the cloud session it is bridged to (`bridgeSessionId`; Agent Monitor takes only whether one is named, to say Remote Control is on). This is the same set of records the `claude agents --json` command reports; Agent Monitor reads the files directly and never spawns the CLI. `procStart` is checked against the live process to unmask registry entries whose PID the system has recycled for an unrelated process; `startedAt` provides the displayed age for fresh sessions that have no transcript yet. What `procStart` *holds* differs per system: a 100 ns tick count on Windows, and on Linux exactly field 22 of `/proc/<pid>/stat` (`starttime`, ticks since boot). A process that is not shut down cleanly leaves its file behind, so a chat reopened several times can own several files. The overview shows a row for each running process of a session and ignores its leftover files; if none is running, only the most recently started one is kept. A session ID exists from the moment a window opens - the transcript file only appears with the first prompt, which is why a "New" session is not stale even though `claude --resume` reports no conversation for it.
- **Transcripts** - `projects/<project-slug>/<session-id>.jsonl`. The project slug is the working directory with every character that is not a letter or digit - the drive colon, path separators, dots, and any other punctuation - replaced by a single hyphen (e.g. `d:\WebDev\oku3d-app` becomes `d--WebDev-oku3d-app`, and `d:\WebDev\HexEd.it` becomes `d--WebDev-HexEd-it`). The slug is that of the directory the session was **launched** in, and it stays that way: when a session switches into a git worktree, the registry reports the worktree as its working directory, but the transcript, subagent files, task output and scratchpad stay under the launch directory's slug. Agent Monitor therefore looks the transcript up by its session id when it is not where the registry's directory points, takes the launch directory from the `worktree-state` entry Claude Code writes on the switch, and files the session under that project - with the worktree named in its details.
- **Model catalog** - `cache/model-catalog/*.json`, the model list Claude Code caches for its own model picker. Only each model's id and context-window size (`runtime.max_input_tokens`) are taken, so the context of the latest reply can be shown as a share of its window. The table is re-read at most once a minute; without a catalog the context is shown as a token count alone.
- **Last self-update** - `.last-update-result.json`, where Claude Code records the outcome of updating its own install. Only whether it succeeded and the version it moved to are taken. A live session is marked as outdated when a restart would bring a newer version: one its root's CLI install moved to (this applies to CLI sessions only, since VS Code and Claude Desktop bring their own copy), or one another live session of the same app on the same root already runs. VS Code, its Insiders build and Cursor are compared separately, because each updates its extension on its own.
- **Process list** - one scan of the process table per snapshot tells, for every session at once: whether its process is still alive, whether it currently has a child process (a tool actually executing), and which application hosts it **right now** (ancestor chain). On Windows that is one Toolhelp snapshot plus `psutil`; on Linux it is one pass over `/proc`, opening only each process's own `stat` file. For a WSL distro, read over the network share, it walks down from the session processes instead, through each thread's list of children, so the distro's other processes are never read. Only names, parent links and start times are read either way - never a command line. A shell between the session process and its GUI host marks the session as CLI-driven - so a conversation resumed with `claude --resume` in a terminal is labeled by where it runs at this moment, not by where it was originally started.

Each transcript is read in full once, to add up its token usage, to find its title and permission mode, and to count the files the agent edited and how often its context was compacted, and to collect the artifacts it published - Claude Code writes an artifact's title and address only when it first appears. The same pass adds up the lines each edit added and removed (from the change Claude Code records with every edit result, and a subagent's own totals), notes when each turn started and when its final reply ended it, and logs the messages the session sent to and received from other sessions and its subagents. The worked intervals of the last day become the timeline in the details; the time between them is the time the session waited. After that only newly appended lines are read. The transcripts of a session's subagents are read the same way, because a session's cost is what its own conversation and every subagent spent. For the cost breakdown each reply's usage is also filed under the skill its turn ran under, and a web search's count of searches is added at the price `pricing.json` gives it. The details that describe the session's current state - its git branch, the latest reply's effort level and context size, when its prompt cache lapses, a Claude Desktop agent's plan step, queued prompts, a dollar budget, failing hooks with the first line of their error output, artifacts and linked pull requests - come from the newest entries alone, like the status. So do the call the session runs or waits on - the newest tool call without a result, described by its command, path, questions or plan - and the text of its newest reply. The prompt cache lapses one lifetime after the newest reply that read or wrote it, and that lifetime - 5 minutes or 1 hour - is the one the newest cache write used; once it has passed, the next request writes the whole context again at the cache-write rate. Every transcript but a tiny one gets that first read on a background thread, so the window shows every session right away: the selected session first, then the most recently active ones. Until the read has finished, that session's cost shows as `…`, and its title and permission mode come from the last 16 MB of the file. The read is done in 1 MB chunks, so even a transcript of several hundred megabytes never sits in memory whole, and it pauses while the window builds a snapshot.

The live overview above is built entirely from the session registry, so it only ever shows sessions that still have a registry record. The **Older** section (closed by default) adds the past sessions that no longer do: opening it triggers a one-time, on-demand scan of the transcripts under `projects/`, skipping any session already shown live. Claude Desktop on Windows keeps its own copy of the chats it runs inside WSL, in a separate folder. If both copies exist, the one in the project's own folder is listed. Each past transcript, and each of its subagents', is read once through the same scan as a live session: that resolves its title exactly as Claude Code shows it (a rename can sit anywhere in the file) and adds up its cost. Its working directory groups it under its project, and the last entries give its model, branch and activity time. The scan runs on a worker thread, so the window never blocks, and the result is cached, so it is paid only the first time you open the section.

The time window chosen in that section sets how far back it reaches, 24 hours by default. That window is not just a display filter: a transcript whose file has not been written inside it is skipped on its timestamp alone and never opened, so the default window reads only the last day's sessions instead of every session ever run. Narrowing the window is answered from the already-fetched result; only widening it scans again.

## WSL sessions

Everything in this section applies to a Windows host. WSL is a Windows feature, so on Linux none of it runs: a Linux machine's sessions are the local ones, discovered exactly as described above.

Everything above works the same way for a Claude Code session running natively inside a WSL distribution - a `claude` process whose own working directory and `.claude` configuration live inside the distribution's own Linux filesystem, not merely a Windows session whose Bash tool happens to invoke WSL for a command. Status, cost, subagents, history, search, and deletion all work identically; only where the files are read from differs. All of it depends on the `wsl` setting (see [configuration.md](configuration.md)), which is on by default. Turning it off also stops the periodic reads described below, which can otherwise keep a watched distribution from idling out.

The machine you run on is one **session root**; on Windows a second is added for every currently *running* WSL distribution that has a `.claude` directory - `home/<user>/.claude` under every user account, plus `root/.claude` for the root account, each its own root, read over the same `\\wsl.localhost\<distro>\...` path Windows exposes for a distribution that is already running. The first root found for a distribution keeps the plain origin `wsl:<distro>`; a second Claude-configured account on the same distribution (unusual, but possible) gets `wsl:<distro>:<home>`, so the common single-account case stays simple. Every session record carries this `origin` (`'local'` or `'wsl:<distro>'`) and `origin_label` (the distribution's name; `None` for the local root); the UI uses it to label the row's host - a WSL session shows its distribution name suffixed "(WSL)" (e.g. "Ubuntu (WSL)") instead of a detected editor or terminal - and every action taken on a session (deleting it, searching it, opening its folder, focusing its window) carries the same `origin` back so it always resolves against the right root, never a different one.

Opening a path under `\\wsl.localhost\<distro>\` starts that distribution if it is not already running, so Agent Monitor only ever looks at one listed by `wsl.exe --list --running --quiet`. That command is the one program it ever runs, invoked by its absolute `System32` path, with fixed arguments, a hidden window, and a five-second timeout.

Two gates keep this near-free while WSL is not in use. A dedicated process-table pass - separate from the per-snapshot scan described above, and cached for five seconds - checks for a shared `vmmem*` process (the WSL2 utility VM); without it, no distribution can be running, so `wsl.exe` is never invoked at all. Once `vmmem` is seen, the running-distribution list itself is cached for 10 seconds, so a poll every few seconds does not re-run `wsl.exe` every time. When a check finds `vmmem` gone, both caches drop immediately, so a VM shutdown is noticed at most five seconds later instead of lingering for the ten-second discovery window.

One limitation is accepted rather than engineered away. If one distribution is stopped while another keeps the shared VM alive, a poll landing inside that 10-second cache window can still show the stopped one as running and read it once, which restarts it. It settles back down on its own: once it drops out of the `--running` list, nothing here keeps touching it, so it idles itself out again shortly after.

A WSL session's registry record carries the same `procStart` field a Windows one does, but it means something else there - the procfs `starttime` described above - read directly over the same UNC mount, no subprocess involved. A pid missing from `/proc` is not alive. If a pid is present but its `stat` field 22 does not match the registry's `procStart`, Linux recycled it for an unrelated process, so it reads not alive too - the same recycled-pid guard the Windows probe applies, adapted to procfs's own field.

Selecting a WSL session with background processes reads the same procfs mount further, on demand: each descendant's memory size and accumulated CPU time, sampled from the same `stat` entries the liveness probe already reads. Procfs has no instantaneous CPU figure, only a running tick count, so CPU is sampled the same way as a Windows process - against the previous reading, with the first sample reading as unknown. Converting those ticks, and the RSS page count, into seconds and bytes assumes the kernel's default 100 Hz clock tick and 4 KiB page size rather than querying either value, since querying would mean running a program inside the distribution. A distro with different values only skews the displayed CPU and uptime figures, never liveness, which compares raw `starttime` values directly.

The background-task output console reads from that root's own temp directory rather than the Windows one - a WSL root's temp directory is the distribution's own `/tmp`, so a session's task-output files and scratchpad live under `\\wsl.localhost\<distro>\tmp\claude-<uid>\...` (Claude Code appends the owner's uid on a shared POSIX `/tmp`, where the Windows temp directory already belongs to one user). The same redirect-confinement rule applies: when a task's own output file is empty, its redirect target is followed only inside that session's own scratchpad or project directory, with the target translated to its Windows-readable form first - a `/mnt/<drive>/...` mount, or any other absolute path inside the distribution.

Search, history, and deletion all resolve a session's files against *that session's own root* - never a different one. A working directory or session id is confined the same way it is on Windows (the resolved path must sit inside that root's own `projects/` directory), so a crafted value can reach neither another root's files nor anywhere outside `projects/`. An origin naming a distribution that is no longer running resolves to nothing and is refused outright, never silently redirected to another root.

## Deleting a past session

From the details or the menu of a history entry - and only a history entry - you can permanently delete that session, after a confirmation. This removes its transcript (`projects/<slug>/<session-id>.jsonl`) and its subagent folder (`projects/<slug>/<session-id>/`) from disk, which also drops it from Claude Code's `--resume` list. It is the only action in the whole tool that writes anything to your Claude files; everything else is strictly read-only.

It is guarded so it can never harm a live conversation: the session id is validated as a UUID, the target paths are confined to `projects/`, and - immediately before deleting - the registry is re-checked so a session that has a live process is refused outright. A running session's files are therefore never touched.

## Determining status

Status is derived **structurally**, from *what the newest transcript entry is* - never from how long ago it was written. Elapsed silence carries no signal here: the model can think for minutes and write nothing, so a long pause looks identical on disk to a finished turn. Only two things hand control back to you - an assistant turn that ended with `end_turn`, and the fixed marker Claude Code writes when you interrupt a turn. In every other live state the model still owes a response and reads as **Working** - including a just-sent prompt, a tool result it is still reasoning about, or a silent thinking phase.

The derivation, in order (the first match wins):

| Newest transcript entry / signal | Status |
|----------------------------------|--------|
| the process has exited | **Finished** |
| no transcript yet (fresh window, no prompt) | **New** |
| the interrupt marker `[Request interrupted by user]` | **Interrupted** - you stopped the turn, so control is back with you (this wins even when the interrupt left a tool call unfinished) |
| a trailing turn flagged as an API error | **Error** - the turn stopped on an API error and nothing is running; the status names the cause where the error record identifies one (**Usage limit reached** for a 429, otherwise **Error: servers overloaded**, **Error: server-side problem**, **Error: request rejected**, **Error: authentication failed**, or **Error: HTTP nnn**), and stays a plain **Error** where it does not; the details add the error's own message line. A usage limit whose error record says which limit it was and when it resets counts down to that reset (**5-hour limit - resets in 2h 10m**) and, once it has passed, reads **5-hour limit reset - you can continue** (this wins even when the error left a tool call unfinished) |
| the newest turn was written before the Claude Code process now holding the session started - the session was reopened after an earlier process ended | **Idle** - nothing that process began is still running (the reply it owed, the call it left open or the dialog it showed died with it), and this one has not taken a turn yet |
| a pending tool that is a question or plan dialog (`AskUserQuestion`, `ExitPlanMode`) | blocked - **Question for you** or **Plan review** (dialogs block in every mode) |
| a pending generic tool in Manual (`default`) mode, or a pending command, fetch or MCP call in Auto-edit (`acceptEdits`) mode | **Permission needed** - Auto-edit is auto-*edit*, not auto-everything: it waives the prompt for file edits only, so everything else still asks |
| a pending file edit in Auto-edit mode, a pending generic tool in Auto / Bypass / Plan / Don't-ask mode, or a pending call with a child process, a subagent or a workflow running behind it | **Working** - the tool is executing (nothing here prompts) |
| a pending call from the row above that has stood still with nothing running behind it - 90 seconds in Auto mode, five minutes in the others | **Waiting for you** - a permission prompt is open, or the session was left mid-call. Auto mode's window is shorter because its classifier answers in seconds, and it does still prompt: an explicit ask rule, an MCP tool that needs your input, or the pause after repeated classifier blocks |
| a finished assistant turn (`end_turn`) that Claude Desktop's turn-ending call marked as blocked | **Blocked - needs your decision** - the agent cannot go on without you |
| a finished assistant turn (`end_turn`) | **Idle** - the agent handed control back, your turn; **Finished with a question** when Claude Desktop's turn-ending call asked you something |
| a fresh user prompt, a tool result, or a mid-loop assistant turn | **Working** - a prompt just arrived, or generation is under way; **Retrying (2/10)** or **Offline - retrying (2/10)** while Claude Code retries a failed request |
| a transcript with nothing interpretable | **Unknown** |

An earlier attempt to flip a quiet session to "your turn" after a fixed freshness window was removed for exactly this reason. The standing-still row above is not that rule returning: it applies only while a tool call is unanswered, and a thinking phase has no open call. An even earlier attempt to read the process's CPU/I-O rates (to detect silent server-side generation) was removed too - the VS Code extension host produces background I/O in the idle `claude` process, so it false-positived and showed idle sessions as working.

Entries of embedded subagent conversations (sidechains) are ignored for state derivation - only the main conversation drives the status.

When a turn has finished or was interrupted but work is still running in the background - a subagent, or a watched child process such as a build - the session reads as **Background** rather than your turn, so a still-busy session is never mistaken for a finished one. An interrupt kills in-process subagents, and so does the end of a reopened session's earlier process, so only a surviving OS child process keeps such a session in Background.

A self-paced `/loop` ends each turn by scheduling its next run (`ScheduleWakeup`, with a delay in seconds). While that run is still ahead, the finished turn reads as **Wakes in 4m** under **Background**: the agent goes on by itself, so it is not your turn. The deadline is the one Claude Code wrote - the call's time plus its delay - so this is not a silence rule; a thinking session is never touched, because its turn has not ended. A wakeup does not count once the session was reopened (it lived in the earlier process), after an interrupt, or when the turn ended on a question or a block.

Some registry records additionally carry a `status` field (`busy`/`idle`, or `waiting` with a reason) maintained by Claude Code itself. When present it refines the derived status: `busy` reads as **Working**, `idle` as **Idle**, and a `waiting` record whose reason names a prompt as **Permission needed**. The last one is essential: Claude Code marks a session blocked on you *before* the pending tool request reaches the transcript, and worktree sessions share one transcript between two processes, which the transcript alone cannot tell apart. A detected permission prompt, an interrupt, or an API error is never overridden, and a `New` session is never demoted. When the `waiting` reason is `input needed` - which current Claude Code writes for an open question only - the label reads **Question for you**; a `permission prompt` reason stays the neutral **Waiting for you**, because earlier versions wrote it for questions too. The record's `statusUpdatedAt` says how long the session has held its status; the details show it ("for 12m") wherever the registry and the transcript agree on the status. The same place names what started a running turn when it was not you: a finished background task, or a message from another session.

Auto mode carries one further state worth showing. Its classifier can refuse a tool call, and after three refusals in a row Claude Code stops deferring to it and prompts you about everything until you approve one. Each refusal is written to the transcript with its own reason field, so Agent Monitor counts the run - any tool that actually ran ends it - and marks the mode as paused. Only that field is read; the refusal text beside it is not. A refusal from a subagent, one you issued yourself, and one from a deny rule are all counted separately from the classifier's, and none of them ends a run.

Time since last activity is taken from the newest transcript entry's own timestamp (Claude Code records these in UTC), falling back to the file's modification time only when no entry carries a parseable timestamp. Reading the entry rather than the file mtime is deliberate: an idle process that rewrites session metadata in place bumps the file's mtime without appending a turn, and that must not reset the age. The displayed ages tick forward every second in the UI between refreshes.

Refresh cadence: a full snapshot is built every `poll_interval` seconds (default 5), so a change no fingerprint can see is still caught within one poll. In between, a cheap fingerprint (registry records plus transcript mtimes/sizes - a handful of `stat()` calls) is probed every second, and any change triggers an immediate full refresh. This reacts within about a second while staying nearly free when nothing happens. A filesystem watcher was deliberately not used: transcript appends during generation would fire event storms, watcher buffers can overflow and drop events, and some changes produce no transcript file event at all - a process exiting, or a background child process starting or finishing - so a periodic full poll is needed either way.

## Subagents

Subagents (from the `Agent` tool and from workflows) do not run as separate OS processes - they run inside the Claude Code process, so a child-process count would not see them. Instead, Claude Code writes each subagent's transcript under `projects/<project>/<session>/subagents/` (workflow agents nested under `workflows/<wf>/`), each with a small `meta.json` (`agentType`, `description`, `toolUseId`).

Agent Monitor counts, per session, the subagents whose transcript was written very recently (running) and those that finished within the last few minutes - so a burst of 20 parallel agents shows how many are still running. The details list what each running subagent is doing, taken from its `meta.json` `description`. For the status only timestamps, the last entry's control fields and those two `meta.json` fields are read. Progress *within* a subagent is not shown - nothing records it.

A session's cost includes its subagents. Every subagent transcript - running or long finished - is added up like the session's own, and the cost breakdown names how much went to each `agentType`. Only usage numbers, the model and the skill name are taken from those transcripts.

## Jumping to a session

Clicking a session activates the window it runs in: the live ancestor chain supplies the host processes, their visible top-level windows are enumerated, and for hosts that keep several windows in one process (VS Code, JetBrains IDEs) the window whose title mentions the session's project folder is preferred. This works for any host reachable through the process chain, even ones the label table does not know.

On Linux the window list comes from the X server - the window manager's `_NET_CLIENT_LIST`, with each window's owning process id and title - and the raise is one `_NET_ACTIVE_WINDOW` request. Applications drawn by XWayland, which is where VS Code and most terminals still run in a Wayland session, are found this way as usual. A window belonging to a native Wayland client is not in that list and cannot be raised: no Wayland protocol lets one application enumerate or activate another's windows.

For sessions of the VS Code extension the jump is **tab-exact**: after raising the right window, the extension's official deep link (`vscode://anthropic.claude-code/open?session=<id>`, available since extension v2.1.72) focuses the session's tab. The window is raised first because VS Code routes the deep link to the currently focused window. Session ids are strictly validated as UUIDs before the URI is launched.

A background agent, started with `claude --bg`, is the one live session with nothing to jump to: it runs under the agent daemon with no terminal and no window. It has no window to switch to, and its details and menu copy the `claude attach <id>` command that opens it in a terminal instead. Background agents are also the one kind that reports a status of its own in the registry, which the derivation above then only has to confirm.

Limitations: CLI-driven sessions get window-level jumps. On Linux the terminal emulator usually sits on the process chain, so the ancestor search finds its window directly; on Windows a console window belongs to a `conhost.exe` child of the shell, so the session title is matched against terminal window titles instead. Windows Terminal does offer `wt -w <window> focus-tab -t <index>`, but exposes no way to enumerate windows or tabs externally - and targeting a non-existent window silently creates a new one - so it is deliberately not used.

## A note on coupling

The session registry, the project-slug scheme, the temp-directory layout, and the transcript schema are undocumented Claude Code internals and can change between versions - and, as `procStart` shows, one field can mean different things on different systems. Agent Monitor parses them defensively - a missing or renamed field yields an `unknown` status or a skipped session rather than an error. If a Claude Code update ever changes the layout, the tool degrades gracefully instead of crashing.

## Uncommitted changes

When you select a session, Agent Monitor runs `git rev-parse --show-toplevel`, `git status --porcelain=v1 --branch -z` and `git diff --numstat -z HEAD` in its working directory - the worktree it switched into, if any. It repeats them every five seconds while the session stays selected, never on the regular refresh. `GIT_OPTIONAL_LOCKS=0` keeps `git status` from writing the index. The files the session edited, collected by the transcript scan, are matched against git's list, which gives the count of the session's own edits that are still uncommitted.

## Test results

The task list reads the last 16 KB of each background task's output and looks, from the end, for the summary line a test runner prints: pytest's `=== 3 failed, 41 passed in 2.1s ===`, unittest's `Ran N tests` followed by `OK` or `FAILED (...)`, Jest's and Vitest's `Tests:` line, the `pass`/`fail` counts of Node's test runner and TAP, cargo's `test result:` line, and go test's per-package `ok`/`FAIL` lines. The newest summary wins, so a test run in watch mode shows its latest result.

## Connection graph

The graph draws each running session with every subagent it ran within the time window chosen above it (1 hour to everything, 24 hours at first), and each of its background processes under the process that started it - a process the count leaves out, such as a console host, is skipped and its children move up to the next one shown. Click a process to see its name, PID, parent process and live CPU, memory and uptime in the details, above the session's whole process table; a row of that table selects its process too. The tools a session or a subagent called within the window hang off that caller as nodes of their own - one per tool, one per MCP server - each with its number of calls, and with moving dots when the last call was within a minute. They are drawn for what you select: a session's own tools and those of all its subagents, or a single subagent's. Starting a subagent, sending a message and handing a result back are drawn as connections and marks, not as tools. A tool with failed calls says how many and is framed in red. Click a tool to narrow its caller's activity in the details to that tool's calls - the details scroll to it - and the filter in the block's header lifts it again. A session's own activity lists the steps from the end of its transcript, so a long conversation shows its newest ones. In the activity a failed call is red, with its command's exit code when it gave one; a call you rejected or one stopped before it finished is yellow. A subagent started by another subagent hangs off that one, and the agents of a workflow run sit under one workflow node. A session that switched into a git worktree files the subagents it started there under the worktree's project folder, so those folders are read too. A running subagent always shows, and so does the agent that started a subagent in the window. The subagents are numbered and drawn top to bottom in the order they started. Each is titled by its task description, or by the skill it ran when it has none, and lists its model, its cost and when it was last active. Click one to see it in the details: whether it runs, its type, skill, model and effort, whether it was started in the foreground, in the background or as a forked skill, which agent started it, its cost, runtime and start time, its tool calls and changed lines, its result (the report it returned, or its latest reply while it runs), its whole task, and its activity: every tool call in order, with when it happened, how long it took and whether it failed, opening to its whole request and result, with its replies in between. Messages within the window connect the sender and the receiver: a session named by its name, a former name or its messaging address from the registry, or a node of its own for a peer outside the list. A message that arrives while a turn runs counts as well. Two nodes share one dashed connection whichever way their messages went, with an arrowhead at each end that received one, so a one-way exchange has one arrowhead and a conversation has two. A subagent has one connection to the agent that started it, and what came back is marked on it just outside the subagent's box. An arrowhead pointing back means it reported its result: a subagent started in the foreground (or a forked skill) by the result its call returned, a background one by its hand-back or the task notification Claude Code sends when it ends. A red cross means that notification says it was stopped, killed or failed, and no mark means no report arrived. An arrowhead into the box counts messages sent to it. A connection carries moving dots while its subagent or process runs, or within a minute of a message, and fades once it has been quiet for an hour. Hovering a connection lists what it stands for - how a subagent was started, what came back, the messages each way and when it was last active - and the legend below the graph, which its button shows and hides, explains every line, mark and box. Press and move anywhere on the graph to pan it sideways and up and down; a press without a move still selects the node under it. The arrow at a session's right edge folds its subagents, processes and tools away - the session then says how many - and the buttons above the graph fold or unfold every session at once; what is folded is remembered.

Replies, plans and subagent tasks in the details are rendered as Markdown - headings, lists, tables, code, quotes - or shown as written, chosen in the header of the box; the choice applies to every such box and is remembered. A link in the text shows its address as a tooltip and is not opened.
