# Project Guidelines

Apply Python best practices and clean code principles. Only change code relevant to the prompt.
Prioritize readability and auditability - this tool reads local Claude Code data, and users must be able to verify at a glance that it never talks to the network, keeps everything on the machine, reads conversation content only for an explicit, on-demand search (which reports back only matching session ids, never any text - see Security & Transparency), and writes to only three places on disk - the **two sanctioned surfaces** its own code touches (the WebView2 UI-preference profile and one explicit, user-initiated deletion of a past session) plus the single-file build's own temp extraction, which no application code performs - see Security & Transparency. `PRIVACY.md` counts the same three.

## Platform
- Windows-only application - no `sys.platform` checks or cross-platform guards needed
- Windows APIs (`ctypes.windll`, `winreg`) can be used unconditionally

## Purpose & Scope
- Local viewer of running Claude Code sessions grouped by project, with each session's live status (working / waiting for you / permission needed / finished); plus, on demand, the **past (non-live) sessions** under a "History" filter, from which a session can be deleted (the one write action touching your Claude Code files - see Security & Transparency); plus a **content search** that narrows the view to sessions whose transcript contains a string (see Security & Transparency for its encapsulation)
- Fully offline: no network, no credentials, no API. State is derived only from the local session registry and transcript control-metadata under `CLAUDE_CONFIG_DIR` (default `~/.claude/`); that state now spans multiple **session roots** - the native Windows install plus one root per currently running WSL distribution that has a `.claude` directory (`roots.py`, `wsl.py`)
- The live backend entry point for the UI is `snapshot.build_snapshot()` - it returns a flat list of **raw** per-session records; the UI (`ui/logic.js`) derives status, labels, grouping and sorting. Everything returned is JSON-serializable and content-free. The **History** listing is a separate, on-demand entry point (`history.list_history()`, exposed as the `get_history` bridge method) that returns the *same* raw record shape (marked `is_history`, always `alive: False`) for past transcripts, deduped against the live registry; the UI folds it into the same `groupProjects`/`buildSession` pipeline. It is fetched only while the (default-off) History chip is enabled, so the potentially large `projects/` scan never runs on the per-second poll. It is additionally bounded by the chip's **time window** (`list_history(max_age_seconds)`, 24 h by default): a transcript whose file mtime predates the window is skipped on its `stat()` alone and never opened, so the scan is proportional to the window rather than to the number of sessions ever run (measured on 270 past sessions: ~2.0 s unbounded -> ~0.2 s at 24 h). The window is enforced twice on purpose - the mtime prefilter is the **looser** of the two (an in-place metadata rewrite can bump the mtime without appending a turn), so it may admit a session the exact `age_seconds` filter then drops, but never the reverse; the exact filter runs *after* `_resolve_folder_cwd`, so a read-but-out-of-window sibling can still donate the folder's cwd. A malformed window value degrades to "no window" (`_valid_window`) - the listing is then merely larger, never wrongly empty
- The **content search** is a third, on-demand entry point (`search.run_search`, driven by the `start_search` bridge method). It is the one path that reads conversation text, so it is tightly encapsulated: it scans only the transcripts of the sessions **currently shown** - the ones the active filter chips display (the UI passes exactly that scoped set, so a session hidden by a filter is never even read), streams progress and matches back through `window.__amcSearchPush`, and reports **only matching session ids** - no text ever crosses the bridge. The UI holds that id set and intersects it with the displayed sessions. Because the scope is the visible set, toggling a chip re-runs an active search over the new scope. The one exception is the **widening offer** on an empty result (`logic.searchWideningStep`, `index.js` `widenSearch`): a search that matched nothing is a dead end precisely because its scope is the visible set. `logic.emptyStateMarkup` therefore tells the two emptiness reasons apart - a query that matched nothing gets `search_no_match`, never the chip-blaming `empty_filter` - and offers one button that adds exactly one step - `hidden` lifts the chip filter off the *scope* (`searchScopeRefs`'s `includeHidden`, which also pulls the past sessions in whether or not their chip is on), then `range` moves one `HISTORY_RANGES` window further back; `null` means everything is already covered and no button is shown. It is a per-**query** grant (`state.searchIncludeHidden`), not a chip change: a chip toggle keeps it, `setSearchQuery` drops it on any edit to the text, and the chips are never touched - which is what makes the widened rows vanish again when the query is cleared. `resetWidenedSearch` (the notice's reset) gives it back without touching the query, and deliberately does **not** re-scan - the rows go because `widened` is false again, and re-reading files already answered for would cost a progress bar and a full row flicker for an undo; it prunes `searchMatches` to the chip-defined scope instead, so the set keeps describing exactly what was searched and the chip counts cannot go on reporting matches in sessions no longer read. A widened search still refreshes itself: `rescanForNewMatches` passes the same flag, so its delta scope is every **live** session rather than the chip-visible ones, and a session that only now starts matching appears on its own - under the notice count if its chip is off, as an ordinary row if it is on. The extra hits are let past the row filter in `render` (`isWidenedHit`, only for a *settled* match, or a pending query would flash every hidden session), counted while selecting, and announced above the panels (`logic.widenedNoticeMarkup`, whose count is plural-invariant by construction - label first, number last - like every other counted label here) - without that line a row whose chip is off reads as a filter that stopped working. The escalation is one step per click on purpose: the chips hide sessions already in memory, whereas a wider window means re-scanning `projects/`, so a user who finds what they wanted after step one never pays for step two The scan is dispatched on a daemon thread so the window never blocks, and the files themselves are scanned concurrently on a `ThreadPoolExecutor` (`_MAX_WORKERS` 32, capped by `cpu_count * 4` and the file count); `pool.map` yields in submission order, so matches are still emitted strictly newest-transcript-first despite running in parallel. A superseded query cancels itself via a monotonic `seq`
- An active search **refreshes itself** when the snapshot changes (`rescanForNewMatches`, hooked off the fingerprint poll in `checkForChanges`), so a match that only just appeared shows up on its own. It exploits that transcripts are **append-only**: an existing match never stops matching, and a new match can only appear in a live session that has grown - so the delta scope is just the chip-visible **live** sessions **not already matched** (dead history is never re-read, matched sessions are skipped). It runs silently (no progress bar) and only **adds** to the match set, so nothing already shown flickers. This is also why the "narrow to the previous hits when the query is extended" optimization was deliberately **not** taken: it assumes files do not change between searches, which contradicts this live refresh (and the gain is marginal given how small the scoped set already is)
- The search query carries the familiar editor **options** (mirroring VS Code): match case, whole word, use regular expression (`options` in `start_search`, persisted in the UI). All three compile into one Python regex, and matching is **line-based** (a JSONL line is one entry - what an editor's search means, and what keeps a regex match well-defined without chunk reassembly). An **invalid** regular expression is reported back as an `error` flag (the UI turns the box red) and no file is ever read for it; the UI also pre-validates with the JS engine for instant feedback. Matching is case-insensitive unless match-case is set (`re.IGNORECASE`, so it is not the full casefold - `ß` does not match `ss`)

## Data & Privacy (pragmatic, not dogmatic)
- What actually keeps this safe: it is **fully local** (no network, nothing leaves the machine), reads **no credentials**, and is **read-only on disk bar two sanctioned write surfaces** in its own code (the WebView2 UI-preference profile, and an explicit user-initiated deletion of a past session's own files) - three disk locations in total, counting the single-file build's temp extraction that the launcher, not this code, performs. Those guarantees are non-negotiable - see Security & Transparency.
- Snapshot and history stay strictly **content-free**. Three encapsulated reads step outside that: the **content search** (`search.py`) reads transcript text to match a query but reports back **only matching session ids** (no text, no snippet - the content-free guarantee still holds for everything that crosses the bridge), guarded by `tests/test_search.py`; the **background-task output** panel (`tasks.py`) deliberately *does* surface process output text, but only that - process output, never conversation - on an explicit per-task expand, guarded by `tests/test_tasks.py` (see Security & Transparency); and the **API-error detail** (`transcript.py` `_api_error_detail`) puts one line of text on the snapshot itself - the first line of a trailing `isApiErrorMessage` entry's own message, clipped to `_ERROR_DETAIL_MAX_CHARS` (160) - because the error's wording carries what its token and status cannot: which limit was hit and when it resets, or which of the invalid-request cases applied. That line is CLI-generated text rather than conversation (such turns are written locally, with `model: <synthetic>`), it is shown only as the tooltip's second line, and it is read only for an entry carrying that flag; `tests/test_transcript_privacy.py` guards the bound (first line of the first text block; a second line, a further block, and an ordinary turn all stay unread). All three read locally; nothing leaves the machine.
- Within that, read whatever a feature genuinely needs from the local Claude Code files - but **only what it needs**, not gratuitously. Prefer the smallest field that answers the question (a `stop_reason` over a whole message, an `agent-*.meta.json` `description` over a subagent transcript). Don't build elaborate workarounds to avoid reading a field a feature legitimately requires.
- `transcript.py` reads mostly control-flow metadata (entry `type`, `stop_reason`, tool IDs/name, timestamps, `message.model`, `message.usage`, `permissionMode`) plus a few display fields that mirror Claude Code's own UI: the session title (`customTitle` > `aiTitle` > first prompt via `_prompt_display_parts`, stripped and truncated), subagent `description`s, and the trailing API-error entry's own message line (`_api_error_detail`, see the content-free bullet above). That is fine - it is shown locally, exactly as Claude Code shows it, and never transmitted. The History path adds one field, the session `cwd` (`history_state_for`/`_scan_title_cwd`): a path, not conversation content, needed only to group a past session under its project when no registry record carries it. That scan reads the whole file once (a rename can sit anywhere) but parses only title-bearing lines, the first prompt, and the first `cwd` - never the usage of every turn, so it stays roughly twice as fast as a full `state_for`.
- `tests/test_transcript_privacy.py` still guards against *accidental* broad reads: markers planted in message text / tool results must not leak into the snapshot, so a careless "dump the whole entry" change gets caught. Keep it as a guard, not as a purity mandate - update it deliberately when a feature needs a new field.

## Claude Code Internals (unversioned - parse defensively)
- The session registry (`~/.claude/sessions/*.json`), the `cwd` -> project-slug scheme, and the transcript JSONL schema are undocumented Claude Code internals that can change without notice
- All parsing degrades gracefully: a missing, renamed, or mistyped field yields status `unknown` or a skipped record - never a crash. Use `(data.get(...) or default)` and `isinstance` checks
- The registry's `procStart` (a 100 ns tick count) is validated against the live process start time in `process_probe` - a mismatch means Windows recycled the PID and the record is stale (session reported as not alive). Its **zero point is version-dependent** - a live example of the silent internal change this section warns about: current Claude Code writes a Windows **FILETIME** (since 1601-01-01 UTC), earlier versions wrote **.NET ticks of the local wall clock** (since year 1). `_ticks_match_epoch` tries both readings and accepts either within the tolerance; the zero points lie ~1600 years apart, so one value can never satisfy both and accepting either cannot weaken the recycled-PID guard. Getting this wrong fails silently and globally: a FILETIME read as .NET ticks lands in the year 426, every session reads as not alive, and since `deriveStatus` gates every refinement behind `alive`, they all collapse to `completed` ("Quiet") while their subagent/workflow badges keep showing. `startedAt` (epoch ms) supplies the displayed age for `NEW` sessions that have no transcript yet. On a WSL root the same `procStart` field means something else entirely - it is exactly field 22 (`starttime`) of `/proc/<pid>/stat`, ticks since boot rather than a wall-clock timestamp - so `wsl.py` compares it against that field directly instead of going through `process_probe`'s .NET-ticks conversion. Parsing `/proc/<pid>/stat` is just as defensive as everything else in this section: a missing pid, an unreadable `stat` file, or a line that does not parse all degrade to "not alive" or a skipped entry, never a crash
- Confine this knowledge: file locations and the `cwd_to_slug` mapping live in `paths.py`; transcript field names in `transcript.py`; registry field names in `sessions.py`. Keep it that way

## Status Model (canonical reference)
- **Status derivation lives in the UI, not Python.** `snapshot.build_snapshot()` returns raw per-session records; `ui/logic.js` derives the status. Python never classifies. Status values (strings): `working`, `processing`, `interrupted`, `errored`, `awaiting_input`, `awaiting_permission`, `new`, `completed`, `unknown`
- **Guiding principle (structural, not time-based):** two states mean "your turn", both read from *what the newest entry is*, never from elapsed time - an assistant turn that ended with `end_turn` (the model finished, status `awaiting_input`/"Idle"), and the fixed **interrupt marker** (`[Request interrupted by user]`, surfaced by the parser as `last_entry_kind === 'user_interrupt'`; the user stopped the turn, so control is back with them and the model owes nothing). The interrupt is its **own** status `interrupted` (yellow, own filter chip), not folded into `awaiting_input`, so a session abandoned mid-task is told apart from a clean finish. In every other live state the model owes a response and is therefore `working` - a just-sent user prompt, a `tool_result` it is still reasoning about, or a long silent **thinking** phase. Elapsed silence must never read as "done": thinking writes nothing to the transcript for minutes, so a five-minute think looks identical on disk to an idle session. There is deliberately no freshness/time input **except** the narrow `stalled` case documented under the pending-tool rule below, which fires only while a `tool_use` is unanswered - never on silence alone, so a thinking session is never touched by it. This is also why the interrupt is detected by its marker and not by time: on disk an interrupt marker is just another `user` turn, indistinguishable from a fresh prompt, so a time rule would flip thinking sessions to "your turn" - exactly the earlier `fresh`-window heuristic (flipped after ~90 s) that this replaced. A **local command** (a slash/`!` command that runs outside the model) is the one other non-`working` structural signal: its execution record means no reply is owed, so the trailing command entry reads `awaiting_input` instead of a pending prompt. Claude Code writes that record in **two** shapes and both must yield the kind - a `system` entry with `subtype: local_command`, and (for `/compact`, which emits no `system` record at all) an ordinary `user` entry whose text opens with `<local-command-stdout>`/`<local-command-stderr>`, matched by prefix in `_is_local_command_output`. Only the *output* wrapper counts: a `<command-name>` invocation is how a prompt-style slash command (`/loop ...`) briefs the model, and that one genuinely awaits a reply, so it stays `user_text`. Getting this wrong is permanent rather than transient - nothing is ever appended after a command that ended the session, so the misread `working` never clears. (An even earlier CPU/IO heuristic was removed too - the VS Code extension host produces background I/O in the idle `claude` process.)
- `logic.classify()` is pure and tested (`tests/js/logic.test.js`), in order:
  - process not alive -> `completed`
  - no transcript (fresh window, no prompt yet) -> `new`
  - newest entry is the interrupt marker (`last_entry_kind === 'user_interrupt'`) -> `interrupted`. Checked **before** the pending-tool rule: an interrupt can leave a `tool_use` unresolved, but the trailing marker means the whole turn was stopped, so it wins
  - newest entry is an API-error turn (`last_entry_kind === 'api_error'`, a trailing `isApiErrorMessage` assistant entry) -> `errored`. Also checked **before** the pending-tool rule: the error stopped the turn even if it left a `tool_use` unresolved. The parser also passes the error turn's own two structural fields through - the error token (`api_error_kind`, from `error`) and the HTTP status (`api_error_status`, from `apiErrorStatus`, read as a number or a digit string) - and **classifies neither**: `logic.apiErrorLabel` turns them into the label, because "Error" alone says nothing about what to do next. It reads the **status first** (the more specific of the two: Claude Code writes a 529 overload as a plain `server_error`), then the token, then the 5xx family, so a usage limit keeps its own standalone `status_usage_limit` ("Usage limit reached" - a wait to sit out, not a fault to report), a named cause reads `status_errored_reason` ("Error: {reason}" over `error_overloaded`/`error_server`/`error_invalid_request`/`error_auth`), an unrecognized token with a status falls back to `error_http` ("HTTP 521"), and nothing identifiable at all keeps the plain `status_errored`. Both maps are `Map`s, not objects: the token is untrusted on-disk data, and an object lookup would resolve `constructor`/`toString` to an inherited value. The raw token is deliberately **never** shown - it is an untranslated internal name, and the fallback chain above means a future one degrades to the status or to "Error" instead. The error's own wording is read as a third field, bounded (`api_error_detail`, `transcript.py` `_api_error_detail`) and shown as the **tooltip's second line** only (`logic.statusTip` -> `status_tip`, which `index.js` puts on the dot and the hero link; the row and the panel header keep the short `status_label`, both being single-line). It is the label's complement, never its source - the label stays structural, so a reworded CLI message can never move the status wording - and it is dropped for any status but `errored`, since it describes a stopped turn. None of the three fields is guaranteed (a lost connection has no status), and all are cleared by any later entry, so a mid-conversation error the CLI retried is superseded by the later real turn and only a *trailing* error reads as `errored`
  - pending tool (last `tool_use` has no matching `tool_result`): `awaiting_permission` when blocking, else `working`. `logic.pendingIsBlocking(toolName, permissionMode)`: question/plan dialogs (`AskUserQuestion`, `Exit/EnterPlanMode`) block in every mode; a generic tool blocks only in a **prompting mode** (`PROMPTING_MODES`: `default` and `acceptEdits`). `acceptEdits` is in that set because it is auto-*edit*, not auto-everything: it waives the prompt for the file-editing tools (`AUTO_EDIT_TOOLS`: `Edit`/`MultiEdit`/`Write`/`NotebookEdit`) and for nothing else, so a pending command, fetch or MCP call in that mode is a prompt. Reading it as a blanket allow was silent and permanent - nothing is appended while a prompt waits, so the misread `working` never cleared and only the `stalled` fallback below caught it, five minutes late. In `auto`/`bypassPermissions`/`plan` (and unknown - an absent mode is treated as non-prompting, the calmer reading) a pending generic tool is executing, never a prompt. A child process (`child_count > 0`) means a **generic** tool is executing, not blocking - as does work running **in-process** (`logic.inProcessWorkRunning`: a running subagent, or an active workflow bridging a fan-out pause), which is the same gate for a pending `Task` call: it spawns no child to prove it is executing, and no mode ever prompts for it, so without this gate the wider prompting set above would report every auto-edit session with a working subagent as blocked (and the `stalled` window below would read the main transcript's standstill as an abandoned call). It deliberately carries **no** force-stop guard, unlike the two readers of the same fields below: `classify` settles an interrupt or an API error before it ever consults the pending-tool reason, and the reason's tool name is read only for a session that came out of `classify` as `awaiting_permission`, so a phantom count cannot reach a stopped session from here. A dialog tool never spawns a child nor a subagent, so background work alongside a pending dialog is unrelated and the dialog still blocks (checked before both gates). All of this is one function, `logic.pendingBlockReason(raw)`, returning **why** it blocks (`dialog` / `prompt` / `stalled`) or `null`; the reason, not just the boolean, is what the label needs (see below)
  - **The one place elapsed time enters the status model** is the third reason, `stalled` (`logic.pendingIsStalled`, `STALLED_PENDING_SECONDS` 300): a pending `tool_use` with **no child process** whose transcript has not grown for that long is not a tool executing. Past that point only two readings remain - an open permission dialog, or a session abandoned mid-call - and both put the ball in the user's court, so it reads `awaiting_permission` rather than claiming the agent works. This does **not** reopen the `fresh`-window heuristic the guiding principle rejects, and the difference is exactly why it is safe: that rule flipped sessions on silence alone, which is indistinguishable from thinking; this one fires only while a `tool_use` is **unanswered**, and a thinking phase has no open call, so the case the doctrine protects is untouched. The failure it fixes is permanent, not transient - nothing is ever appended after an abandoned call, so the misread `working` never clears on its own (observed on a VS Code session for days). Two guards keep it narrow: a live child means a genuinely long build/test run keeps reading `working` however old the entry is, and a non-finite age never counts as stalled. The known cost: an in-process call that legitimately outlasts the window with no child to show for it (a slow MCP tool whose server started with the session, so `_is_session_helper` excludes it from `child_count`) reads as blocked - deliberately traded for never leaving an abandoned session on `working`
  - the label follows the **reason**, not the status: `buildSession` passes `logic.namedPendingTool(raw)` to `attentionLabel`, which is the tool name only for `dialog`/`prompt`. A `stalled` call names no tool, so it falls through to the neutral `status_needs_you` ("Waiting for you") - the same treatment as the registry-`waiting` route, and for the same reason: nothing here says a *permission* is what it waits for
  - newest entry is an assistant `end_turn` -> `awaiting_input`
  - newest entry is a **local command** (`last_entry_kind === 'local_command'`, from either shape of a slash/`!` command's execution record - see the guiding principle above) -> `awaiting_input`. A local command runs outside the model - Claude Code even writes a caveat telling it not to respond - so no reply is owed; without this rule the trailing command `user` entry would misread as a pending prompt and stick on `working`. It can briefly read idle while a prompt-style command's first turn is still being thought out, but that is transient, unlike a permanently stuck `working`
  - newest entry is `user_text` / `tool_result` / a non-`end_turn` assistant turn -> `working`
  - otherwise `awaiting_input` if there was any activity, else `unknown`
- `logic.refineWithNative()` applies the registry's native `status` field after `classify`: `busy` -> `working`, `idle` -> `awaiting_input`, and `waiting` (only when the registry also gives a `waitingFor` reason) -> `awaiting_permission`; never overrides `awaiting_permission`, `interrupted`, or `errored` (all definitive - the interrupt marker or an API-error turn being newest means no turn is running, so a lagging registry `busy`/`idle` must not flip or flatten it), never demotes `new`. The `waiting` case is essential because Claude Code marks a session blocked on a permission prompt *before* the pending `tool_use` reaches the transcript, so the structural rule still sees the fresh user prompt and would read `working`; the registry is authoritative that the agent is blocked on you. `waiting_for` is read in `sessions.py` (registry field `waitingFor`) and passed through the snapshot. Also essential for worktree sessions where two processes share one transcript. Note: VS Code sessions usually have **no** native status (`null`), which is exactly why the structural rule above (not the registry) must detect thinking
- `logic.refineWithBackgroundWork()` promotes `awaiting_input`/`unknown`/`interrupted` -> `processing` when a subagent is running, a background **workflow** is still active (`logic.activeWorkflows` over the snapshot's `workflows`), or the session has a child process. So a finished turn with work still running in the background does not read as "your turn". Force-stop caveat: after a force-stopped turn (`user_interrupt` or `api_error` - a usage limit stops the whole CLI), `deriveStatus` and `buildSession` treat `subagents_running` as 0 **and drop any active workflow** - in-process subagents and workflows die with the stop, so a still-"running" count or "active" workflow is a phantom the recent window has yet to clear and must not promote the session (nor show a running/workflow badge). A detached OS **child process** can outlive the stop, so `child_count` still counts; an interrupted session with real surviving background work does read as `processing`, whereas `errored` is deliberately **not** in the promotable set (a stuck-on-error session stays `errored` so the error stays the salient signal, never masked as `processing`)
- The permission mode is the latest `permissionMode` field seen anywhere in the transcript (tracked in the incremental scanner in `transcript.py`); absent -> treated as non-prompting. Shown per session via `logic.modeLabel`. Claude Code records it in **two** shapes and a session can write only one of them, so keying on the entry type alone reads the mode of some sessions and not others: the **CLI** logs a Shift+Tab switch as its own `type: permission-mode` entry, while a **VS Code** session never writes that entry at all and instead stamps the mode in force onto each ordinary entry (a `user` turn carries `permissionMode` beside `timestamp`/`cwd`). Both say the same thing about the same point in the file, so `_absorb_line` reads the field wherever it appears - last one wins - rather than branching per entrypoint; `isSidechain` entries are skipped, since a subagent's turns do not report the main conversation's mode. The failure this fixes is silent and asymmetric: a VS Code session in `default` mode reads as mode-less, and `pendingIsBlocking` treats an absent mode as non-prompting, so a waiting permission dialog reads `working` unless the registry's `waiting` signal happens to catch it
- The tail parser (`transcript.py`) escalates its window (256 KB -> 2 MB -> 16 MB) when nothing parses; sidechain entries (`isSidechain: true`) are skipped for state, model, and title - only usage counts them. Injected `isMeta` entries (the local-command "DO NOT respond" caveat, continuation summaries) are likewise skipped for state, so an injected notice never reads as a pending prompt
- **Subagents** (`subagents.py`): counts running and recently-finished subagents per session from `projects/<slug>/<session>/subagents/` (recursively, incl. `workflows/<wf>/`). An `agent-*.jsonl` older than `SUBAGENT_RECENT_SECONDS` is skipped (long finished); within the window, `_is_finished(path, age)` decides via the transcript's **last entry** (from the tail): an assistant `tool_use` block with nothing after it means a tool is executing -> **running**; a natural stop (`_DONE_STOP_REASONS`: `end_turn`/`stop_sequence`) -> **finished**; otherwise (an answered turn, e.g. a workflow agent's final `StructuredOutput` tool call whose `tool_result` is the last entry) -> **finished only once the file has been quiet for `_SUBAGENT_SETTLE_SECONDS`** (so a normal think/tool pause is not misread as done). Keying "finished" on a trailing `end_turn` alone (the old behaviour) left completed workflow agents - whose last act is a `StructuredOutput` tool call, not an `end_turn` - stuck as running until the recent window expired. Reads only control fields (entry `type`, `stop_reason`, block `type`) and each agent's sibling `agent-<id>.meta.json` (`agentType`/`description`, resolved in `_label` as `agent_path.stem + '.meta.json'` - not a plain `meta.json`) - never the subagent's conversation content. Alongside the counts it reports `running_age`, the freshest **running** agent file's age (clamped at 0 against clock skew), which `snapshot._display_age` folds into the session's age - see the age bullet below. For a **workflow** (`workflows/<run>/`) this per-agent-file view leaves a gap between fan-out phases where no single agent is momentarily running, which would flicker the whole session between `working` and "your turn"; so each run's `journal.jsonl` is also read as a workflow-level signal (`_workflow_activity`/`_journal_counts`): its one `started` and one `result` event per agent give the run's `total` agent count and whether it is still `active` (`total > done`, or the journal written within `_WORKFLOW_GRACE_SECONDS` to bridge the phase pause; a run quiet past `SUBAGENT_RECENT_SECONDS` is dropped as finished). The snapshot ships this as `workflows` (`[{run_id, total, done, active}]`); the UI drives the ⚡ badge count (the workflow's total) and the "Background" promotion from it, and the badge tooltip shows progress as `done`/`total`. Only each event's `type`/`agentId` decide the counts - a `result` payload (the agent's returned content) is never accessed or surfaced; `_journal_counts` caches by the journal's size+mtime, so the append-only file is re-parsed only when it grows
- **Background processes** (`process_probe`): `child_count` is the number of the session's meaningful descendant processes (excluding `conhost.exe`) - a watched build/scan. OS processes, **not** subagents (which run in-process); the two badges are distinct. `snapshot.py` gets the count from `process_probe.probe_all` for a Windows root, `wsl.probe_wsl_sessions` for a WSL root (dispatched on `root.proc_dir`) - same meaning, different process table. The snapshot carries only the count; the per-process detail is an on-demand path (see the process panel below)
- **Process panel (on demand)**: clicking the background-process badge opens a panel driven by three on-demand bridge methods, none on the per-second snapshot poll. (1) `get_process_stats` dispatches the same way as `child_count` above - `process_probe.process_stats(pid)` for a Windows session, `wsl.wsl_process_stats(root, pid, proc_start_ticks)` for a WSL one - either way returning live per-descendant `{pid, name, cpu, rss, uptime}`, the *same* descendant set the badge counts. On the Windows side, a session whose tools run through a `wsl.exe`/`wslhost.exe` relay additionally gets a trailing `kind: 'wsl_vm'` row for the shared `vmmem*` VM (the real Linux work runs in that VM, not as a Windows child, so the relays read idle; the VM figure is machine-wide, which the UI labels) - a native WSL session needs no such row, since `wsl_process_stats` already lists the session's own descendants straight from the distro's `/proc`, real work rather than a stand-in for it elsewhere. CPU is the raw per-process figure (100% = one core): on Windows sampled non-blocking via a cached `psutil.Process` per pid so the first reading is `None` and a real percentage follows a second later; `wsl_process_stats` samples the same way against its own per-origin tick-count cache, ticks converted with the kernel's assumed 100 Hz `CLK_TCK`, and is recycled-pid aware via the same `starttime` guard the liveness probe uses. (2) `tasks.list_tasks` (bridge `get_tasks`) lists the session's background-task output files with size and last-write age, freshest first, plus each task's label. The UI passes the oldest running process's uptime (plus a small grace) as `max_age`, so a task last written before any current process started - a leftover from an earlier run - is dropped as irrelevant (`recent_seconds`). (3) `tasks.read_task_output` (bridge `read_task_output`) returns the tail of one task's output, read **only** while its row is expanded - see Security & Transparency. The UI renders that tail as **escaped** HTML (`logic.ansiToHtml`, tested in `tests/js/logic.test.js`): ANSI SGR color codes become spans with a **fixed** set of themed `.ansi-*` classes, other control sequences (cursor moves, line erases) are dropped, and every text run goes through `logic.esc` - so nothing from the output ever reaches markup unescaped or an attribute. The rendered text stays selectable (Ctrl+C copies the code-stripped text the browser sees); the per-second refresh is skipped while a selection is active inside the console, so a selection is never clobbered mid-copy
- "Needs your attention" = `awaiting_input` union `awaiting_permission` union `interrupted` union `errored` (`logic.needsAttention`)
- Labels are tone-accurate: `awaiting_input` reads as "Idle" (the agent finished; nothing is mandatory) with a calmer text color, and `awaiting_permission` is refined by the pending tool's name (`logic.attentionLabel`): `AskUserQuestion` -> question dialog, plan-mode tools -> plan review, any other known tool -> permission prompt. When `awaiting_permission` comes from the registry `waiting` signal there is **no** pending tool to name (and `waitingFor` reports `permission prompt` even for a plain question), so the label stays neutral (`status_needs_you`, "Waiting for you") rather than claiming a permission is needed. There is no separate legend: the toolbar has one filter chip per status color (`FILTER_DEFS`, mapped by `logic.filterBucket`) and each chip's dot doubles as the color key. The whole `awaiting_permission` band lives under the "Needs you" chip (`filter_needs`, orange dot); `errored` under its own "Error" chip (`filter_errored`, red dot - the strongest alarm colour, since an error stopping the CLI outranks a blocked prompt); `interrupted` under its own "Interrupted" chip (`filter_interrupted`, yellow dot - the warm attention colours run red -> orange -> yellow -> green from errored through blocked and interrupted to idle), `awaiting_input` under "Idle" (green), `processing` under "Background", `completed`/`unknown` under "Quiet", and `new` under its own "New" chip (`FILTER_DEFS` label `status_new`, `dot-new` colour) - a regular chip like the rest, on by default and unchecked to hide, not a separate visibility toggle. `interrupted` is a "your turn" state (it stays in the quiet `STATUS_BAND` for project ordering, like `awaiting_input`) but keeps its own colour and chip so an abandoned-mid-task session is spotted at a glance and can be filtered on its own; `errored` behaves the same way (own colour and chip, quiet `STATUS_BAND`) so a session stuck on a usage limit or API error stands out too. The **History** chip - labelled **"Older"** in the UI (`filter_history`; the internal key stays `history` everywhere, including the persisted `amc-filter` selection, so only the label was renamed: a browser's "history" means everything ever opened, current pages included, whereas this chip is exactly the complement of the other chips) - is the one exception to "one chip per status colour": a past session is `completed` but is routed to it by `logic.sessionBucket` (which returns `history` for an `is_history` record, else falls through to `filterBucket`), keeping the on-demand history listing separate from the recently-ended sessions the live snapshot still carries under "Quiet". It is also the one chip **off by default** (`FILTER_DEFS` `offByDefault`, so `DEFAULT_FILTER_KEYS` excludes it) - enabling it is what triggers the `get_history` fetch (`index.js` `ensureHistoryLoaded`, guarded by `state.historyLoading`, cached in `state.history`). It is likewise the one **split** chip (`historyChipMarkup`, `.filter-chip-split`): one shell so the pair reads as a single control, the left half toggling the chip and the right half opening the **time window** menu (`logic.HISTORY_RANGES`, default `24h`, persisted as `amc-history-range`). The shell is a plain element because a button cannot contain a button. Picking a window also switches the chip on - the range half is otherwise a dead end while the chip is off. Only *widening* re-fetches (`logic.historyRangeCovered` against `state.historyLoadedSeconds`); narrowing is served from the cache by `logic.filterHistoryByAge`, which every reader of history goes through (`visibleHistory()`) so the raw cache is only ever touched by the fetch and by a deletion. It filters on the ages frozen at fetch time, so rows do not shed themselves as they tick past the boundary. Because the window bounds the search scope too, the empty state names it (`historyWindowHint`, `history_range_hint`). The chip's **width must not change when it is switched on**, or the chip row rewraps under the cursor that just clicked it - which takes two things: History is the one bucket whose sessions are absent from the grouped set while its chip is off, so `render` counts them separately from the same cache (`historyRows`, narrowed by the search exactly as every other chip's count is), and the badge keeps its slot at zero via a hidden `.count-placeholder` (there is genuinely no count before the first scan - producing one would mean running the very scan the chip exists to defer). `.chip-range-label` carries a `min-width` for the same reason
- **Panel order** (`logic.sortProjects`, priority mode): attention band (`projectBand` - the project's most urgent session) first, then **newest activity** (`projectActivityAge` - the freshest session's `age_seconds`), then the name as a tie-break. Ordering within a band by name looks like the stable choice but is not: a panel that finishes its work leaves the busy band and jumps to wherever the alphabet puts it, i.e. into the middle of a long list at the exact moment you were watching it. By age it slides one position down instead - every panel's age grows at the same rate, so the order shifts only when a panel genuinely gains activity (its age drops to ~0 and it leads its band) or crosses a band boundary. A non-finite age (missing, or `NaN` from a mistyped snapshot value) must never reach the comparator, which would return `NaN` and leave the order undefined - `projectActivityAge` maps it to `Infinity`, so it sorts last and falls through to the name. With the priority toggle **off** it is a plain alphabetical list: neither band nor age has a say, which is the point of the toggle
- Age is computed in Python (`transcript._activity_age`) from the newest transcript entry's `timestamp`, parsed to POSIX seconds in `_timestamp_epoch`: Claude Code records timestamps in UTC, so the trailing `Z` is normalized to an explicit offset (a value with no offset is read as UTC) and the result compares directly to `time.time()`. It falls back to the file mtime **only** when no entry carries a parseable timestamp. Deriving from the entry timestamp rather than the mtime is deliberate: an idle process (e.g. the VS Code extension host) that rewrites session metadata in place bumps the file mtime without appending a turn, and that must not reset the "last activity" age. `build_snapshot` ships the numeric age; the UI formats and ticks it
- **Only a conversational turn's timestamp counts** (`_TURN_ENTRY_TYPES`: `assistant`, `user`, `system` - exactly the types `_parse` derives `last_entry_kind` from, so age and status read the same entries). Claude Code also *appends* bookkeeping entries - `queue-operation`, `file-history-snapshot`/`-delta`, `ai-title` - and letting one of those set the timestamp is the same mistake the mtime rule above avoids, merely arriving as an appended line instead of an in-place rewrite: a `file-history-delta` lands whenever any tool writes a file (a subagent writing to the scratchpad included), which would report the conversation as having moved when it did not. An unknown type is treated as bookkeeping - the quieter reading, since a new conversational type would leave the age standing rather than refresh it on something that never happened. Consequence for the status: a transcript holding *only* bookkeeping reports `has_activity: false`, so `classify` returns `unknown` ("Quiet") rather than `awaiting_input` - an untouched session no longer claims a reply is owed on the strength of a queue record
- **A turn delegated to a subagent keeps the session's age fresh** (`snapshot._display_age`, fed by `SubagentInfo.running_age`): while the whole turn runs inside a subagent, the session appends nothing to its *own* transcript - observed at twelve minutes - so the transcript age alone reports it as untouched while it plainly works, and the panel order (`projectActivityAge`) sinks it accordingly. `count_subagents` therefore also reports the freshest **running** agent file's age (it already `stat()`s each one, so this is no new read), and the displayed age is whichever of the two is fresher. Only a running agent contributes, and only under a **live** process: once an agent returns, the main transcript carries the turn again and its own age is the honest one, and a subagent runs in-process, so a still-"running" agent under a dead process is the same phantom the UI already discounts after a force-stopped turn - counting its file age would make a session that ended mid-delegation read as seconds old for the rest of `SUBAGENT_RECENT_SECONDS` (guarded in `tests/test_snapshot.py`). Retention is deliberately untouched by all this: `_include_ended` keeps deciding on the raw transcript age, so the fresher age can only ever change what an ended session *displays*, never how long it is kept. The status was always right here - `refineWithBackgroundWork` promotes the session to `processing` - this is about the age and the ordering that follows it
- **How long an ended session stays visible is a different clock from its age** (`snapshot._include_ended`, `ENDED_MAX_AGE`). The window runs from when the session *ended* - approximated by the last poll that saw its process alive, remembered in memory by `last_seen.py` (`note_alive`/`seconds_since_alive`, keyed `(origin, session_id)` on `time.monotonic`, pruned alongside the scan cache). Keying it on the transcript **activity age** instead - the previous rule, still the fallback for a session this process never saw alive - drops a session that sat idle for hours and was then closed in the very same poll that noticed it ended, which is exactly the session someone who closed a window by accident wants back. An activity age is always *older* than the moment the process ended, so consulting the sighting can only ever lengthen the window, never shorten it. Nothing of this reaches disk: it is a process-local dict, so a restart just falls back to the activity age
- `logic.classify()`/`deriveStatus()` take only plain data, no DOM/IO - keep them pure so they stay Node-testable

## Token Usage & Cost
- `transcript.py` sums usage across every assistant turn (subagents included) into an overall total **and** a per-model split (`usage_by_model`), because subagents often run on a cheaper model than the main session - a single rate on the combined total would be wrong. Cache-creation tokens are also split by TTL (`cache_creation_5m/1h_input_tokens`) from the nested `usage.cache_creation`, since 5m and 1h writes are priced differently
- Claude Code writes locally-generated assistant turns (interrupts, injected notices) with `message.model == "<synthetic>"` and zero usage. That sentinel is **not a real model**: `transcript.py` (`_SYNTHETIC_MODEL`) excludes it from the displayed `model`, the per-model split, and the history, and `logic.sessionCostUsd` also skips any zero-usage model so a placeholder can never force the whole session to the token-total fallback
- `transcript.py` also builds `model_timeline` - the **main conversation**'s chronological model-switch log (sidechain/subagent turns and the synthetic sentinel excluded, unlike `usage_by_model`). Each main-conversation assistant turn is a `(timestamp, model)` event; `_run_timeline` sorts them by time (transcript entries are not strictly ordered on disk, so order is resolved here) and run-length compresses into one `{time, model}` entry per contiguous run. So a model left and returned to appears **more than once** and the *last* entry is the current model with the time it was switched back to - unlike the earlier `model_first_seen` (per-model minimum), which collapsed the return and could leave a no-longer-used model as the newest entry. Only these few switch points cross the bridge (reduced Python-side, like the old field). `logic.modelHistory` just formats labels (`formatModel`), keeping the order; `buildSession` sets `model_switched` (>1 run)/`model_history`; the UI shows "(+N)" after the model, hover listing each run's model and switch time (via `fmtDateTime`)
- `transcript.py` builds `cli_timeline` the same way for the **Claude Code version** each turn was written by (the per-entry `version` field): both switch logs go through the one `_run_timeline(events, value_key)`, keyed by `_MODEL_KEY`/`_CLI_VERSION_KEY` (those strings are wire format - the UI reads `entry.model`/`entry.version`). Two differences from the model: the sentinel exclusion does **not** apply (a `<synthetic>` turn means "no real model", but it was still written by a real CLI, so its version is valid evidence), and the *current* value is read by the **tail** parser as `cli_version` - which is what lets a History record show a version at all, since `history_state_for` never runs the full scan that a timeline needs (`cli_timeline` is `[]` there, matching `history.py`). `logic.cliHistory` passes the runs through; `buildSession` sets `cli_version`/`cli_switched`/`cli_history`
- **A timeline is memoized, and `_scan_appended` copies the state only for a real partial line** (`_ScanState.timeline_cache`/`timeline()`, guarded by `tests/test_scan_appended.py`). Both matter for the **per-second** poll cost, and only became visible with a second timeline: building one sorts *every* event and parses each timestamp for the sort key, so a session with thousands of turns paid tens of milliseconds per poll per timeline, on top of a `copy()` of both event lists. The event lists are append-only, so an unchanged **count** means an unchanged timeline; and a transcript normally ends on a newline, so `trailing` is empty and there is nothing to absorb into a copy - reporting off the cached state instead is what lets its memo survive the poll (building it on a copy that is then discarded is why the memo silently did nothing at first). Measured on a 53 MB / 8.7k-turn transcript: ~27 ms per poll -> ~0.2 ms, and the initial full scan ~770 ms -> ~260 ms. `timeline()` hands out fresh dicts, so the snapshot can never mutate the cache
- **The CLI-version column is conditional** - the one column that is not always in the grid. Normally every session runs the same version, where the column would repeat one value down every row, so `logic.cliColumnRelevant(sessions)` (over the **visible** sessions, after filtering) decides: true once the current versions differ *or* any session has `cli_switched`, and `index.js` toggles `.show-cli` on `<body>` before `alignColumns` measures. The CSS adds the track under `@media (min-width: 901px)` rather than next to `.row`, because `body.show-cli .row` outranks the plain `.row` of the narrower breakpoints (a media query adds no specificity) and would otherwise keep a five-column layout alive past the point where the model column already gave up its space. It is a real track, not a `0px` one, because a zero-width column still pays the 13px `gap`
- Prices live in **`pricing.json`** at the repo root (loaded by `pricing.py`, mirroring the `i18n.py` `LOCALE_DIR` pattern; shipped verbatim in the bootstrap payload, bundled via the spec `datas`; mock-supplied in `dev-mock.js`). It is a **hand-maintained offline snapshot** - no network, no live lookup, no pricing URL in code; a `_comment` key documents the format and is stripped on load. Top-level keys are **effective-from dates** (`YYYY-MM-DD`); each is a complete snapshot of `model-key -> {input, output, cache_read, cache_write_5m, cache_write_1h}` in $/MTok (**explicit per-model rates, no multipliers** - the 5m/1h/read prices are listed, so they can differ from the base-input ratios). Model keys are family-version (`opus-4-8`, `sonnet-5`, `haiku-4-5`, `fable-5`, ...) since versions are priced differently (Opus 4.8 != 4.1, Sonnet 5 != 4.6)
- Cost is **derived in `ui/logic.js`**, not Python: `resolvePrices(schedules, dateStr)` picks the schedule with the latest date on or before today (so a future change entered ahead of time takes effect on its own; `index.js` passes the local date and threads the resolved table through `groupProjects`/`buildSession`). `modelPriceKey` maps a model id to its key (strips `claude-`, `[tier]`, trailing snapshot date). `sessionCostUsd` prices each model's usage separately; if **any** model has no rate in the resolved table it returns `null` and the UI shows a plain token total. The 1M-context tier is not modelled (long-context turns undercounted). Cache writes without a TTL split are priced at the 5m rate
- `formatCost` renders whole dollars (`$19`, rounded) or `<$1` below a dollar - the estimate is too coarse for cents or a "~". The row shows this compact cost (or the token-total fallback) by default; a >500ms hover on the usage figure animates it open (CSS grid `0fr`->`1fr`) to the full per-tier breakdown. `buildSession` supplies `usage_compact` (the anchor) and `usage_detail` (the breakdown that slides open before it); `usage_total` is the token count the "Usage" sort uses. Title and usage share one flex column so a long figure shrinks only that row's title

## Window & DPI
- The window is a normal pywebview + WebView2 window - no tray, no tray-anchored positioning, no `SetWindowPos`
- pywebview 6.x `resize()`/`move()` expect **logical pixels** (pywebview applies DPI scaling internally)
- **Window background follows the UI theme, not the system theme** (`window_background.py`): the bare window - form `BackColor`, WebView2 `DefaultBackgroundColor`, and the window-class brush - must match the page's `--bg`, or a mismatched edge shows through while WebView2 lags a resize. Python cannot read the page's stored theme preference, so `window_background_color()` (a read-only registry lookup of the *system* theme) only seeds the initial `create_window` colour; the page then reports its real `--bg` over the `set_window_background` bridge (in `initTheme` on load and on every theme toggle) and `apply_native_background` recolours the live window, marshalled onto the UI thread (the bridge call arrives on a worker thread). All of it is a Win32/WinForms UI operation on the app's own window - no file or registry write. The .NET (`clr`) interop is imported lazily and wrapped best-effort, so it degrades to a no-op off a live host (e.g. in tests)
- **Page layout**: the body is a column flexbox split into a fixed `.topbar` and a single scrolling `.content` region; `html`/`body` are `overflow: hidden` so nothing else ever scrolls. `.content` uses `overflow-y: scroll` (not `auto`) so the scrollbar gutter is always reserved and the layout never shifts sideways. Because `.content` is a flex item, never give it auto cross-axis margins - they disable the stretch and shrink-wrap/center it. Its hero/panels/state slots are always present in the DOM; an empty slot is dropped from the flex flow via `& > :empty` so its `gap` never shows as phantom spacing. Anything appended to `body` at runtime (menu, tooltip, toast, modal) must stay `position: fixed` so it never joins the body flex flow
- The UI is a static asset bundle in `agent_monitor_for_claude/ui/` (`index.html`/`index.css`/`logic.js`/`index.js`); Python exposes raw data via the `js_api` bridge (`app._MonitorApi`). **Python is a pure data provider**: all derivation (status, formatting, grouping, sorting) lives in `ui/logic.js`, which is DOM-free so it runs in the browser and under Node for tests. This includes the **empty-state and notice markup** (`emptyBlock`, `emptyStateMarkup`, `widenedNoticeMarkup` and the widening helpers behind them): they build strings rather than derive data, but they are pure, so they take one plain `view` object - assembled in exactly one place, `index.js` `emptyStateView` - instead of reading `state`, which is what puts the wording rules under `tests/js/logic.test.js` rather than beyond reach in a DOM. `ui/index.js` owns the DOM/bridge side effects and renders via keyed reconciliation (reuse nodes, no full `innerHTML` rebuild) so open menus and scroll position survive a refresh. There is **one** UI HTML file (`index.html`) - no separate dev harness to drift. Opened directly in a browser (a `file://` page, or `index.html?mock`) there is no bridge, so `index.js` loads `ui/dev-mock.js` and renders from its fabricated showcase sessions instead - no Python needed. `dev-mock.js` holds **only** invented session data plus a tiny price snapshot (no labels - the full set lives in `index.js` `DEFAULT_LABELS`, so the preview can't drift), stays mock-only, is never wired to real session data, and is **deliberately excluded from the spec `datas`** so it never ships. New *shipping* UI asset files must be added to the `datas` list in the spec (but never `dev-mock.js`)
- **The page runs under a strict Content-Security-Policy** (the `<meta http-equiv>` in `index.html`): `default-src 'none'` with `connect-src 'none'` (so the engine itself refuses any `fetch`/XHR/WebSocket - the network guarantee is structural, not just an absent call), and `script-src`/`style-src`/`img-src` limited to `'self'`. Consequences for any UI change: **no inline `<script>`** (that is why the page bootstrap lives in `ui/boot.js` for the head and `ui/boot-scripts.js` for the end of body - both loaded without the `?v=` token, since nothing could supply it before they run), no inline `style` attribute in a markup string, no `data:`/`blob:` URI, and no remote resource of any kind. Setting `element.style.*` from JS is unaffected. `'self'` covers the `file://` preview too (verified in Edge), so the policy needs no `file:` source. `window.evaluate_js` is host-injected and not subject to the policy, so the search-result push keeps working
- **Markup is built by string concatenation, so every interpolated value passes through exactly one of two primitives** - `logic.esc` in text position, `logic.attr` for a whole attribute - **numbers included**, so there is no per-value judgement call and an auditor can read the rule off the call site. Both live in `logic.js` because they are pure, which is what puts them under `tests/js/logic.test.js` (the guard tests there assert the escaping contract - do not weaken them); `index.js` aliases them at the top. `esc` escapes `& < > " '` in one pass and is safe in text and in any **quoted** attribute - it is *not* sufficient for an unquoted attribute, for a URL-bearing attribute (`href`/`src`, where `javascript:` needs no metacharacter), or inside `<style>`/`<script>` (both CSP-forbidden anyway). That is why `attr(name, value)` exists and is preferred: it owns the quotes, so a call site cannot pick a quoting style the escaping does not cover, and it is the **only** place in the UI that assembles an attribute. A computed attribute name is injection no value escaping can catch, so `attr` throws on a name that is not a literal identifier. Dynamic values that need no markup at all still belong in `textContent`/`dataset`/`replaceChildren`, which is what most of `index.js` already does
- **CSS uses native nesting** (the target is a single modern WebView2/Chromium, so it is fully supported - no build step, no prefixing). In `index.css`, nest a component's states, children, and variants under its base rule with `&` instead of repeating the parent selector across flat rules. Keep nesting shallow (2-3 levels) and readable; don't nest so deep that a selector's origin is hard to trace
- **Never use the browser's native `title` tooltip.** It is ugly, unthemed, and has an uncontrollable delay and placement. Always use the app's own HTML tooltip: give the element a `data-tip` attribute (newlines become line breaks) and the single delegated handler in `index.js` (`initTooltips`, `.tooltip` in the CSS) shows the shared, themed popup on hover. It is dismissed by the pointer leaving its target, which means a target that leaves the **DOM** dismisses nothing - so `syncTooltip` runs at both `render` exits, next to `syncOpenMenu`/`syncProcPanel` and for the same reason: a render can drop the target (the widened-search notice on reset) or replace it with an equivalent node (`renderFilters` rebuilds its whole chip row every render, after which the later `pointerout` arrives on the new node, fails the `!== tooltipTarget` check and never fires - that one stuck indefinitely). Gone means hide; replaced under a motionless pointer means re-anchor, never blink. Any new floating element appended to `body` needs the same treatment. `document.title` (the window/tab title) is not a tooltip and is fine
- **A destructive confirmation names its target, and never holds the initial focus on the destructive button** (`showConfirm` in `index.js`): the dialog's `.modal-detail` line quotes the row the action came from (`rowCellText` reads the rendered `.name`/`.age` at click time, so it is literally what the user just read; empty detail is dropped from the flow by `&:empty`), and `cancelBtn.focus()` makes the reflex Enter/Space that dismisses an appearing dialog cancel rather than delete. A prompt that states only the *consequence* confirms the intent but not the object, which is the one mistake a list of near-identical rows invites - naming the target is what makes the confirmation load-bearing, not the warning text

## Security & Transparency
- **Read-only bar two sanctioned write surfaces**: no file or registry write in application code beyond these two. Three places on disk are written in total; the third is the build's, not this code's, and is listed as (3) so both this file and `PRIVACY.md` count the same way. (1) The WebView2 profile at `%LOCALAPPDATA%\AgentMonitorForClaude` (`webview.start(private_mode=False, storage_path=...)`), which persists localStorage UI preferences (theme, filter, collapsed panels); without it pywebview's private mode resets them every launch. (2) **Session deletion** (`session_delete.py`, `delete_session`): removes a **past** session's own transcript (`projects/<slug>/<id>.jsonl`) and subagent folder (`projects/<slug>/<id>/`), reached through the `delete_session` bridge in `app.py`, only on an explicit user click in a history row's menu after an in-UI confirmation. It is the sole file-deletion surface and is guarded three ways: the session id must be a UUID, the target paths are confined to `projects/` (resolved and checked with `relative_to`), and the registry is re-probed **immediately before** deleting so a session with a live process is refused outright - a running conversation's files are never touched. No application-code write beyond (1) and (2), and no deletion outside `projects/`, is ever permitted. (3) **The single-file build's temp extraction**: the PyInstaller launcher unpacks the bundle (Python runtime, libraries, UI assets) into `%TEMP%\_MEIxxxxxx` on every start, which is why `app._ui_dir` reads `sys._MEIPASS`. It holds only the app's own files, never user data, and is removed on a normal exit - a hard termination (including the single-instance "replace the running instance" path, which calls `TerminateProcess`) leaves one behind. It is **not** a surface you can add to or remove in code, so it is outside the two-surface rule while still being a place on disk this app writes: count it, do not sanction against it. Two further writes touch no file at all: the **clipboard** (`clipboard.py`, on the row menu's copy action - the session id only) and the **named shared-memory block** the single-instance guard keeps (`single_instance.py`, this process's own pid and version, alongside a named mutex). Neither widens the two-surface rule, but neither is "no write at all" - say so rather than claiming an absolute the code does not hold
- **No network**: no outbound connections of any kind. No `requests`, no URL literals, no external destinations. (pywebview's internal localhost HTTP server that delivers the bundled UI to its own window is the sole, sanctioned socket; with `private_mode=False` it uses pywebview's fixed default port so the localStorage origin stays stable across restarts)
- **No credentials**: never read authentication tokens or other secrets
- **WSL sessions add a read surface, never a write or execution one**: when the `wsl` setting is on (default), Agent Monitor reads a *running* WSL distribution's `.claude` registry/transcripts, `/proc` process metadata (names, parent links, start times, and - on demand, for the process panel - memory and CPU time; never command lines), and its own `/tmp/claude/...` task-output tree (the same on-demand, encapsulated read `tasks.py` performs on Windows, redirect confinement included) over `\\wsl.localhost\<distro>\...`, the same UNC path Windows exposes for an already-running distribution. A distro absent from `wsl.exe --list --running --quiet`'s output is never touched by any filesystem access, so a stopped distribution is never woken (one documented exception: a distro stopped while another keeps the shared VM alive can restart once within the ~10 s discovery-cache window, then idle back out on its own - see `wsl.py`'s module docstring). That `wsl.exe --list --running --quiet` call - invoked by its absolute `System32` path (`_WSL_EXE`; a relative name would resolve through the Win32 process-creation search order, which checks the application directory and cwd before System32), fixed arguments, hidden window, enumeration only - is the **one and only** external program this application ever executes; nothing is ever run *inside* a distribution. Gated behind a `vmmem*` process check (5 s cache) so it costs nothing while WSL is unused. See `PRIVACY.md` for the full statement
- **Background-task output is a sanctioned, encapsulated read that DOES surface text** (`tasks.py`, `read_task_output`, reached through the `read_task_output` bridge): unlike every other read, this one shows process output text in the UI - a deliberate, user-requested relaxation limited to **process output**, never conversation. It reads the live output file Claude Code writes for a `run_in_background` task (`<temp>/claude/<slug>/<session>/tasks/<taskId>.output`, path scheme confined to `paths.py`), locally, and **only while the user has that task's row expanded** (never on the snapshot poll). When that capture file is **empty** because the command redirected its output elsewhere (`... > run.log 2>&1`), the redirect target parsed from the recorded command is read instead - but only if it resolves inside the session's own **scratchpad** or **project cwd** (`_resolve_redirect`, `relative_to` against those two roots; a WSL `/mnt/<drive>/` target is translated to its Windows path first). That is the one widening of the read surface beyond `tasks/`, and it stays within session-owned trees - a redirect anywhere else is ignored. Every path is resolved and checked with `relative_to` against its allowed root, and both the session id (a UUID) and the task id are validated, so a crafted id cannot read outside those trees; only the file tail is read. Task **labels** additionally read the transcript's background Bash `description`/`command` (again process content, not conversation) to name a row instead of showing an opaque id. This is **not** a write and does not widen the sanctioned-write-surfaces rule; `process_stats` (CPU/RAM/uptime) reads process metadata only. `tests/test_tasks.py` guards the boundary (path confinement, id validation, tail-only). A running process's *unwritten* stdout/stderr cannot be shown at all: attaching to a live process's streams after the fact needs invasive DLL-injection/API-hooking or a debugger, which this tool's read-only, non-invasive stance forbids - so the only visible output is what the task already wrote to its file
- **Content search is a sanctioned, encapsulated read** (`search.py`, `run_search`, reached through the `start_search` bridge): it is the one place that reads conversation text, and it exists to answer a single yes/no question per session - does this transcript contain the query? It reads locally, on an explicit user search only, and reports back **only matching session ids and progress counts** via `window.__amcSearchPush` - never a line, a snippet, or any text. No content crosses the bridge, reaches the UI, or (there being no network) leaves the machine. Every transcript path is confined to `projects/` (resolved and checked with `relative_to`, exactly like the deletion surface), so a crafted id/cwd cannot read outside the transcript tree. The scan is scoped to the sessions the UI passes (those in view - or, only after the user clicks the empty result's widening offer, one step beyond them; nothing widens on its own and any edit to the query puts the scope back), is dispatched on a daemon thread and fans the files out over a `ThreadPoolExecutor` while still emitting matches newest-file-first, streams matches as it finds them, and a superseded query cancels itself via the monotonic `seq`. It is **not** a write and does not widen the sanctioned-write-surfaces rule. `tests/test_search.py` guards the boundary (only-ids, path confinement)
- No `eval()`, `exec()`, `compile()`, or dynamic imports; no obfuscation, no base64-encoded strings or tokens. The one dynamic JS execution is `window.evaluate_js` used solely to push search results (a JSON literal) into the page - never arbitrary or interpolated code
- **Window activation** (`window_focus.py`) is a sanctioned capability: Win32 window enumeration and `SetForegroundWindow`, executed only on an explicit user click. Window titles are compared in memory to pick the right window - never stored, logged, or displayed
- **Session deep link** (`window_focus.py`) is the second sanctioned launch surface: `os.startfile` on the official extension URI `vscode://anthropic.claude-code/open?session=<uuid>` (template is a top-level constant), only on user click, with the session id strictly validated as a UUID. It is the only URI **this code** launches; the one other address the app carries is not launched by Python at all (see the changelog link below), and no further URI scheme may be added to `os.startfile` without the same treatment - a top-level template constant and a strictly validated interpolation
- **The changelog link is the only remote address in the code** (`logic.CHANGELOG_URL`, `logic.changelogUrl`): the CLI-version column renders the version as an ordinary `<a target="_blank">` to its section of Claude Code's public changelog. Nothing is ever requested from it - pywebview's `OPEN_EXTERNAL_LINKS_IN_BROWSER` (on by default) handles `NewWindowRequested` and hands the URL to the system browser, so **`target="_blank"` is load-bearing**: a same-window navigation would replace the app's own page. This does not weaken the no-network guarantee (the app opens no connection, and a URL `#fragment` is never sent to a server, so not even the version looked up leaves the machine), but it does mean the guarantee is now phrased as "no HTTP client, no connection" rather than "no URL anywhere" - `PRIVACY.md` says so explicitly and its "Verify it yourself" grep covers the UI files and **expects exactly this one hit**. The version reaching the `href` is untrusted on-disk data, so `changelogUrl` returns a URL only for `^\d+\.\d+\.\d+$` and the column falls back to plain text otherwise - the href can hold nothing but digits and dots (guarded in the HTML-safety group of `tests/js/logic.test.js`). A second remote address is not a small addition: it needs the same validation, the same `PRIVACY.md` accounting, and a reason the user clicked for it
- **Open project folder / scratchpad** (`window_focus.py`, `open_directory`) is the third sanctioned launch surface: `os.startfile` on a session's project `cwd` (the panel-header path text) or its scratchpad directory (the row menu's "Show scratchpad in Explorer", offered only when `scratchpad_path` confirms the dir exists), only on user click, reached through the `open_path` bridge in `app.py`. The path is validated with `os.path.isdir` **before** it reaches the shell, so only a real directory is ever launched - a stale path, a file, or anything carrying a URI scheme is a silent no-op, never something the shell could execute. `open_directory` is the only place a file-system path is handed to `os.startfile`
- **Show a session's transcript in Explorer** (`window_focus.py`, `reveal_in_explorer`, reached through the `reveal_path` bridge) is the same surface for the one **file** it covers - the row menu's "Show transcript in Explorer". It is *shown*, never opened: the path is validated with `os.path.isfile` and handed to the shell's `SHOpenFolderAndSelectItems`, which raises an Explorer window with the item selected, so no program is ever launched for the file and nothing reads it. A failing shell call (an id list the namespace cannot build) degrades to `open_directory` on the containing folder - the same window minus the selection. That is a shell call of the same class as `os.startfile`, **not** a new external program: the `wsl.exe` enumeration stays the one and only program this application executes, and `subprocess`/`explorer.exe /select` is deliberately not the route taken. Which rows get the entry is decided by the `transcript_path` bridge, which returns a path only for an existing file confined to `projects/` (`relative_to`, plus the same UUID check the deletion surface uses) and never opens it - a stat, not a read, and never on the per-poll path (both guarded in `tests/test_app.py`, including a test that fails if the file is ever opened)
- Minimal, well-known dependencies only: `pywebview`, `psutil`. Adding a dependency is a significant decision (see the pre-merge gate)
- Isolate side effects: process access in `process_probe.py`, file reads in `sessions.py`/`transcript.py`/`history.py`/`search.py` (reads content but reports only ids)/`tasks.py` (reads process output and surfaces it, on expand only), the sole file deletion in `session_delete.py`, the one piece of cross-poll memory in `last_seen.py` (in-process only, never disk); keep helper and utility functions pure

## Type Hints & Documentation
- Module docstring as the very first element (title with equals underline, blank line, description)
- `from __future__ import annotations` as the first import (after the module docstring)
- Type hints in function signatures only, not in docstrings
- numpydoc (NumPy-style) docstrings for public functions, classes, and non-trivial methods; skip for trivial 1-3 line methods
- Never mention changes, improvements, or type hints in comments or docstrings
- `# type: ignore` only with a specific error code and short reason: `# type: ignore[code]  # reason`

## Formatting
- PEP8-based with an extended line length of 140-160 characters
- Function signatures and calls on one line when reasonable
- Never use deep indentation to align with a previous line's opening bracket; use 4-space indentation from the statement start
- Single quotes (`'`) default, double (`"`) when containing single quotes, triple-double (`"""`) for docstrings
- Use hyphens (`-`) for dashes in text, never em dashes or en dashes

## Spacing
- Two blank lines between top-level functions/classes, one between methods
- Blank lines separate logical blocks (after guards, before returns)

## Imports
- Three groups separated by blank lines: standard library, third-party, local
- Within groups: `import` before `from...import`, sorted alphabetically
- Relative imports within the `agent_monitor_for_claude` package, except `__main__.py` which uses absolute imports for PyInstaller compatibility

## Structure
- Main exported functions first, then helpers in logical order
- Prefix non-exported helpers with underscore; `__all__` for library modules
- Prefer functional/modular code over classes; no global mutable state
- Descriptive, self-explanatory names - no ambiguous names like `other`, `data2`, `flag`

## List Comprehensions
- Avoid complex comprehensions with multiple conditions or long expressions
- Use explicit loops with guard clauses when there are multiple conditions or repeated calls per item

## Validation & Errors
- Validate inputs at function start; early returns and guard clauses
- Defensively parse all on-disk / external data (see Claude Code Internals)

## Testing
- Two suites, both must pass after any change: the Python backend (`python -m unittest discover -s tests`) **and** the pure UI logic (`node --test tests/js/logic.test.js tests/js/global-scope.test.js`, Node's built-in runner, no extra dependency)
- Fix the code to make tests pass - never weaken or remove tests to avoid failures
- Cover edge cases (missing/renamed fields, empty transcripts, dead PIDs, UTC-vs-local age), not just the happy path
- Load-bearing tests: the Python privacy test (`tests/test_transcript_privacy.py`) guards the content boundary (including that the History scan reads `cwd` but no content, and that the API-error read stays bounded - the first line of the first text block of an `isApiErrorMessage` entry, with a second line, a further block, and every ordinary turn staying unread); `tests/test_search.py` guards the content-search boundary (it reports only session ids, never text, and every read is confined to `projects/`) and must not be weakened; `tests/test_session_delete.py` guards the deletion surface (UUID validation, the live-process refusal, path confinement to `projects/`) and must not be weakened; the status-classification table tests now live in `tests/js/logic.test.js` (they moved with the logic) - extend them when behavior changes. The thinking case (a stale `user_text` entry stays `working`) is explicitly covered there. That file's **HTML safety** group guards the markup boundary (`esc` escapes all five characters in a single pass, `attr` cannot be broken out of and rejects a computed name, `ansiToHtml` keeps untrusted process output as text and emits only allowlisted classes, and the empty-state/notice builders keep hostile label text and a hostile *count* out of the markup) and must not be weakened either - it is what makes the "every interpolated value is escaped" rule above a checked claim rather than a convention. The **empty-state wording** group next to the widening tests is the other half of that move: it pins which reason speaks for an empty view, that a search result never blames the chips, and that the offer escalates one step and then stops
- Python: `unittest` only (stdlib); mock time by patching `time.time()`/`datetime`; use temp dirs plus `CLAUDE_CONFIG_DIR` for file-based tests. JS: `node:test` + `node:assert`, `logic.js` only (no DOM), required into the test via `require('../../agent_monitor_for_claude/ui/logic.js')`
- Tests live in `tests/` (Python) and `tests/js/` (Node), both outside the package and not bundled

## Changelog
- Update `CHANGELOG.md` for every user-facing change; group under `## [Unreleased]` as Added / Changed / Fixed / Removed
- Write from the user's perspective; one bullet per logical change; hyphens for dashes
- **Keep a bullet short - one to three sentences.** A changelog is scanned, not read: state what changed for the user, and for a fix what was wrong, then stop. Leave out the root-cause story, the mechanism, the implementation narrative, and the "why this was hard" - a reader who wants that has the commit. Never restate the same point in different words for emphasis. Mention a detail only when it changes what the user does or expects (a default, a scope, a caveat, a version requirement, an attribution or credit); a measured number earns its place only if it is the point of the change. This is a hard length rule, not a preference - a paragraph-long bullet is a defect to fix, even if every sentence in it is true
- Do not add entries for internal refactors, code style, or documentation-only changes
- Changes to `CLAUDE.md` are invisible to users - never mention them in changelog entries or commit messages

## Releasing
- Update `__version__` in `agent_monitor_for_claude/__init__.py` and all four version fields in `version_info.py` (`filevers`, `prodvers`, `FileVersion`, `ProductVersion`)
- In `CHANGELOG.md`: rename `## [Unreleased]` to `## [x.y.z] - YYYY-MM-DD`, add a fresh empty `## [Unreleased]` above it, and update the compare links
- The GitHub release title is exactly the tag name (`vX.Y.Z`, e.g. `v0.2.0`) - no product-name prefix. As part of a release the user asks for, the assistant may create the tag, the commit, and the push, and create the GitHub release (title = tag name, notes from the version's `CHANGELOG.md` section) with the EXE attached

Do it once the version bump is in place, and never while another build or a running instance is active - concurrent PyInstaller runs lock the `build/` artifacts and fail with `WinError 32`. Verify the built EXE's `FileVersion` matches the release, then attach it to the GitHub release
